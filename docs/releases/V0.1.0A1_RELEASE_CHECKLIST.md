# MTMF v0.1.0a1 release candidate checklist

**Status: NOT RELEASED. Do not tag until every blocking gate below passes.**

## Purpose

Establish a reproducible, pre-onboarding MTMF baseline for ATI's initial single-development-Tenant/single-user integration. This prerelease does **not** claim application-neutral onboarding (PRs 21–26), production root recovery, or production readiness.

## Release changes

- Align workspace and four Python distribution metadata versions to `0.1.0a1`.
- Retain HTTP `/v1` wire contract; no new management endpoints.
- Tag only the validated merge commit as immutable annotated `v0.1.0a1`, after the gates below.

## Blocking packaging issue: client depends on mtmf-api

At this candidate, `packages/mtmf-client/pyproject.toml` declares `mtmf-api==0.1.0a1`. The recommended ATI `uv` source declaration for **only** `mtmf-client` cannot satisfy that dependency from a fresh environment unless `mtmf-api` is independently available through a configured package index or separately declared VCS source.

Before release, **choose and implement an approved solution**:

1. Preferred for the Git-only pre-release: make the consumer dependency graph independently resolvable, for example by declaring **both** `mtmf-client` and `mtmf-api` as explicitly pinned `uv` Git sources using the **same** immutable repository tag and their respective subdirectories. Document the exact consumer `pyproject.toml` snippet in `VERSIONING.md`. The consumer may install the `mtmf-api` contract package transitively; it MUST NOT import internal `mtmf-core`, `mtmf-service`, Rust, or DB components.
2. Alternatively, publish compatible `mtmf-api` wheels to a trusted index before the consumer installation, or perform a separately reviewed extraction of client-facing DTOs that genuinely removes the runtime dependency. Do not silently delete `mtmf-api` from metadata while imports still require it.

**Documentation correction required:** the current `VERSIONING.md` assertion that a Git-only consumer installs `mtmf-client` with no sibling distribution dependency is not satisfied by the current source. Update it to reflect the tested approach before tagging.

## Required release gates

- [ ] Reconcile the `mtmf-api` dependency and demonstrate a fresh **outside-workspace** `uv sync --locked` of a minimal consumer using only the documented Git source(s); no local editable packages or unpublished index dependencies.
- [ ] Regenerate and commit the root `uv.lock` with `uv lock`; verify `uv sync --locked` from a clean checkout. **The lockfile is not regenerated by this metadata-only preparation commit.**
- [ ] Build and install all four wheels, verify their `0.1.0a1` metadata, and import the client in a clean Python 3.14 environment.
- [ ] Run `./build.sh --qa`, `./build.sh --sec`, `./build.sh --rust`, and `./build.sh --integration`; record exact outcomes and environment.
- [ ] Run deployed HTTP/client integration and conformance acceptance applicable to the frozen baseline, including real Keycloak and PostgreSQL; do not represent skipped opt-in tests as executed.
- [ ] Confirm that the intended release commit contains the documentation and source used for acceptance; record any non-production limitations.
- [ ] Merge the release preparation PR only after all blockers are resolved and review is complete.
- [ ] On the merged and validated commit, check `v0.1.0a1` does not already exist, then create/push one immutable annotated tag and record its commit SHA.
- [ ] Pin ATI's dependency source(s) to `v0.1.0a1`, commit ATI's `pyproject.toml` and `uv.lock`, and deploy the MTMF service from the same tagged commit.

## Explicit non-goals

No onboarding PR 21–26 implementation, no new root recovery mechanism, no silent API contract change, no automatic Git tag, and no claim that changing version strings alone constitutes a validated release.
